      01 · THE IDEA

      Make the reader create the data

      The question is easy to say and hard to picture. Design a dimensional model for in-game ad revenue and retention in a mobile music game. Name the grain and the dimensions. Then show how you would check it. A star schema diagram answers it, but nobody remembers a diagram.

      So I flipped it. You install a made-up game, play a song, see an ad, and watch your own taps turn into rows, models, a dashboard and, at the end, bad data that the tests catch.

      02 · THE DATA

      4,000 players who don't exist

      Real game data was never an option, so every number comes from a small generator inside the page. It uses a fixed seed, so you see the same numbers on every visit. Ad prices and country price levels are assumptions.

      4,000made-up players28days–ads in the fake crowd7seed

      I planted one pattern on purpose: players who see more ads on day 0 come back a little less often. That gives the dashboard something real to find, and the page says the pattern was planted.

      Your own play joins the crowd as pink rows, so the totals move when you play. Every tile, chart and test result is calculated from those rows. Only the assumptions, like prices and alarm limits, are typed in.

      03 · THE STACK

      One file, no servers

      The whole demo is one HTML file: plain CSS, plain JavaScript and hand-drawn SVG. No libraries, no build tool and no network calls, so it opens anywhere and sends nothing out.

      The SQL you see is dbt-style BigQuery SQL, written to match each model. The page does not send it anywhere. It does the same maths in JavaScript, so every "run" is simulated.

      04 · THE BUILD

      Five versions to get to a game

      Each version came from one piece of feedback on the version before it.

      V1Star schemaTables and grain as a diagram. Correct, but flat.
      V2Play the gameA phone you can play; ads and events appear as you go.
      V3One storyYour taps flow to tables, models, reports and a break-it graph, with the SQL behind each.
      V4One screenThe picture on the left, its details on the right, no page scroll.
      V5Dashboard + mapA real dashboard, a level map for the daily run, a calmer event list, a tighter phone layout.

      The hardest part was not the SQL. It was fitting a lot of detail on one screen, from a phone to a big monitor, without anything getting cut off.

      05 · THE CHECKS

      How I know it works

      29 browser tests run against the page served as a real website. On 7 laptop sizes, they check that the page never scrolls and nothing gets cut off. On 2 phone sizes, the page scrolls, but nothing spills sideways or out of its card. Other tests check each step by mouse and keyboard, reduced motion, and that the event list no longer flickers.

      The page also checks itself each time it loads: clean data passes all 4 tests, each bug is caught by at least one, and the dashboard tiles match the model's own numbers.

      Then a second AI reviewed each version with the same scoring rules, and I fixed what it found until the score was above 95:

      V4
      77→89→93→95→96

      One honest note: the last V5 step, 95 to 97, was not a fix. The reviewer dropped two deductions it could not point to evidence for.

      06 · THE RECEIPTS

      Am I sure it's right?

      The modelling ideas are standard: decide the grain first, add up each side before a join, and test against a total you trust. The numbers are not real. They show how the calculations work, not what a real game earns.

      Some things I could not check here. The SQL has never run on a real BigQuery warehouse; it was reviewed against the documentation. The page has not been tried with a real screen reader. Inside a chat app, its height is a guess from your screen size, not tested in the real app. If you spot something wrong, I want to know.
